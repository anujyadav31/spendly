# Spec: Registration

## Overview
Make the existing registration page actually create accounts. Today `GET /register`
only renders a form whose POST has nowhere to go. This step adds a `POST /register`
handler that validates the submitted name, email and password, stores a new user with
a werkzeug-hashed password, and redirects to the sign-in page with a success message.
It is the first write path into the `users` table built in Step 1, and it gives Step 3
(Login and Logout) real accounts to authenticate against. No session or "logged-in"
state is created here — signing in is Step 3's job.

## Depends on
- **Step 1 — Database setup**: `users` table (with `UNIQUE` email), `get_db()`,
  `init_db()`, `seed_db()` in `database/db.py`.

## Routes
- `GET /register` — render the empty registration form (already exists; unchanged behaviour) — public
- `POST /register` — validate input, create the user, redirect to `GET /login` with a
  success flash; on failure re-render `register.html` with an error and the previously
  entered name/email — public

Implemented as one view function: `@app.route("/register", methods=["GET", "POST"])`.

## Database changes
No database changes — the `users` table from Step 1 already has every column needed
(`name`, `email UNIQUE`, `password_hash`, `created_at`).

New helpers in `database/db.py` (no schema change):
- `get_user_by_email(email)` → `sqlite3.Row` or `None`
- `create_user(name, email, password)` → new user `id`; hashes the password with
  `generate_password_hash` inside the helper so routes never handle hashing or SQL.
  Lets `sqlite3.IntegrityError` propagate on a duplicate email (race-safe backstop).

Testability tweak: `DB_PATH` reads an optional `SPENDLY_DB_PATH` environment variable,
falling back to the current `expense_tracker.db` path, so tests can use a temp database.

## Rules for implementation
- No SQLAlchemy or ORMs
- Parameterised queries only (`?` placeholders) — never f-strings or `%` in SQL
- Passwords hashed with werkzeug (`generate_password_hash`) — never store or log plaintext
- Use CSS variables — never hardcode hex values
- All templates extend `base.html`
- All DB access lives in `database/db.py`; the route only calls helpers
- `url_for()` for every internal link and form action
- Validation (server-side, in this order, first failure wins):
  1. `name` — stripped, required, max 100 chars
  2. `email` — stripped and lower-cased, required, must contain `@` and a `.` after it
  3. `password` — required, at least 8 characters (not stripped)
  4. `confirm_password` — must exactly equal `password`
  5. email not already registered (`get_user_by_email`)
- Error responses re-render `register.html` with HTTP **400** and a single `error` string
- Catch `sqlite3.IntegrityError` from `create_user` and show the same
  "already registered" error (handles a duplicate slipping past the pre-check)
- On success use Post/Redirect/Get: `flash(..., "success")` then `redirect(url_for("login"))`
- Do not create a session, log the user in, or touch the Step 3+ stub routes
- Currency/locale is INR — any user-facing copy that mentions money uses ₹

## Definition of done
- [ ] `python app.py` starts on port 5001 with no errors
- [ ] `GET /register` renders the form; the form's `action` is generated by `url_for`
- [ ] Submitting a valid name, email and 8+ char password redirects (302) to `/login`
- [ ] `/login` then shows a green "Account created — please sign in" message, once (gone on refresh)
- [ ] The new row exists in `users` with a werkzeug hash in `password_hash`
      (starts with `scrypt:` or `pbkdf2:`), not the plaintext password
- [ ] Email is stored lower-cased and trimmed (`  Foo@Bar.COM ` → `foo@bar.com`)
- [ ] Registering `demo@spendly.com` (or any existing email, any casing) returns 400 with
      "An account with that email already exists" and creates no row
- [ ] Blank name, invalid email, or password under 8 chars each return 400 with a
      specific error message and create no row
- [ ] Mismatched password and confirm password return 400 with "Passwords do not match"
      and create no row
- [ ] After a failed submit, name and email fields keep their values; both password fields are empty
- [ ] Error and success boxes use CSS variables only (no hex in new CSS)
- [ ] `pytest` passes, and the test run does not modify `expense_tracker.db`
